# SPC700 CPU and snapshot foundation

`SPC700` implements all 256 sound-CPU opcodes in Swift. `SPC700Bus` supplies
byte reads, byte writes and idle clocks. Each call represents one clock; dummy
reads are real reads and can have device side effects. A bus must perform the
access before advancing attached devices. The core does not map APU ports,
timers, the IPL overlay or DSP registers.

This ports Gustavo Franco's MIT-licensed
[sony-spc700-python](https://github.com/gufranco/sony-spc700-python/tree/91c0576a00bd7eae09847f8f34bd4ff2dfc46773),
specifically `spc700/core.py` and `spc700/opcodes.py`. The license is in
`ThirdParty/sony-spc700-python-LICENSE` and copied into the app bundle's
`Contents/Resources/Licenses`. Python and libgme are not runtime dependencies.

## Execution contract

Construct a CPU with a bus and explicit `SPC700.Registers`. `step()` executes
one instruction and returns its clocks. `run(cycles:)` executes whole
instructions until its budget is met; the last instruction may overshoot.
Both accumulate `cycles`. `restore(_:)` clears the clock count and halt state
without accessing memory. The owner must restore memory and devices alongside
the registers. CPU instances require a single execution owner.

Default registers are deterministic conveniences, not a hardware reset model.
External interrupts are not implemented. BRK, RETI, EI and DI are implemented
as instructions. SLEEP and STOP follow the corpus's seven-clock finite
observation, then set `stopped`. Further `step()` calls do nothing;
`run(cycles:)` advances idle bus clocks while held. Wakeup and hardware reset
remain outside this API.

## Verification

The independent [SingleStepTests corpus](https://github.com/SingleStepTests/ProcessorTests/tree/bb11756436da8fd16cce86aef63dc6725f48836f/spc700)
was generated by David Schneider's JSMoo. It is pinned at
`bb11756436da8fd16cce86aef63dc6725f48836f`. The Swift port passes all 256,000
cases: final registers and listed RAM bytes, cycle counts, and every recorded
read/write/wait address and defined value. Unspecified read values are not
compared. This is emulator-conformance evidence, not hardware measurement or
proof of complete APU/audio fidelity.

discrepancies and its remaining hardware-validation limitations.

## SPC snapshots

`SPCFile` reads and writes complete v0.30 snapshots using the
[published format](https://snesmusic.org/files/spc_file_format.txt): CPU
registers, 65,536 RAM bytes, 128 DSP registers and 64 extra RAM bytes underneath
the IPL overlay. Extra RAM is **not** the IPL program. Reserved bytes, ID666
header bytes and the trailer are preserved exactly, including binary tags and
opaque xid6 extensions. Tags are not interpreted; trailer validity is not
checked. New snapshots have no ID666 tag.

The parser requires the complete 66,048-byte base file and rejects unsupported
headers, truncation and invalid array sizes. Short 0x10180-byte dumps accepted
by some players are not supported. SPC snapshots omit timer phases and DSP
internal history, so they cannot restore exact execution mid-cycle.

Restoring one (`SSMPBus.init(snapshot:)`, `SDSP.load(registers:counter:)`)
takes CONTROL, the DSP address, port inputs, timer targets and 4-bit outputs
from RAM `$F0-$FF`. Timer dividers and host replies restart at 0, and each
timer prescaler restarts one clock before its tick, the convention SPC players
use (libgme loads every timer with its next tick at clock 1). The S-DSP keeps
the register image, takes KON as written but not yet polled, and restarts its
voices, echo state and schedule (T2). Its rate counter starts at 0 unless the
caller passes another start; libgme's loader is equivalent to `$7F0`. A
restore therefore loses sounding voices and the driver's position inside a
timer period: song `$04` rendered from its own start snapshot runs 14 frames
behind the live render, because timer 0's divider restarts at 0.

Inspect a snapshot without executing it:

```sh
macos_studio/.build/debug/chronoforge music spc-info snapshot.spc --out info.json
```

The JSON contains CPU registers, memory-region hashes and trailer length.
Errors preserve existing output; input and output must differ.

## Normal-speed S-SMP bus and driver execution

`SSMPBus` connects the CPU to 64 KiB RAM, directional host/APU ports, three
timers, an optional caller-supplied 64-byte IPL overlay, and an `SSMPDSPPort`
endpoint. CPU reads/writes and idle cycles advance the timers and endpoint.
Host port operations consume no SMP clocks. Timer outputs are four-bit and
read-clear; enabling resets divider/output but preserves the free-running
prescaler. CONTROL clears incoming port pairs without clearing outgoing replies.
DSP addresses with bit 7 set read the mirrored register and ignore writes.

The implementation follows the existing CPU's **access before clock** contract.
It is a deterministic normal-speed model, not a physical subcycle timing model.
`timersBeforeAccess` (off by default) steps the timers before the access
instead, so a read in the clock a timer ticks sees the new count and an enable
in a prescaler-tick clock misses that tick. That is libgme's order for these
ties; it exists for the comparison below, and which order hardware uses is not
established here.
Construction zeros timer phases and MMIO latches independently of initial RAM;
it does not restore an SPC snapshot or reproduce hardware power-on state.
Nonstandard TEST writes and enabling an absent IPL produce a sticky bus fault.
Callers must inspect `fault` after each instruction and stop; the nonthrowing CPU
interface otherwise continues counting accesses after the bus has frozen.

`CTSPCDriver.check` copies the six payloads identified by the ROM's boot tables
into ARAM and executes the original driver at `$0200`. The CLI requires the
verified USA 1.0 ROM SHA-256 because its checkpoints are revision-specific:

```sh
macos_studio/.build/debug/chronoforge music driver-check re_workspace/ct_clean.sfc \
  --out driver-check.json
re_workspace/.venv/bin/python macos_studio/tools/verify_ssmp_driver.py
```

The diagnostic reaches the first main-loop entry `$0299`, checks initialized
RAM/DSP values, sends an echo-only command, then sends `$FD` to exercise the
driver's DSP-write handler. The S-DSP runs alongside; this diagnostic does not
record its PCM (see `music render`). The first entry
takes 85,396 clocks in the chosen zero-state model: initialization waits for
five timer1 ticks. Execution has a 250,000-clock budget (instruction-boundary
checks; may overshoot by one instruction). Timeouts and bus faults fail.

Without `--ipl` this is **direct-load driver execution**, not song loading or
playback. The evidence and reproduction commands are in the local
workspace (`re_workspace/reports/ssmp_evidence_20261019.md` and
`re_workspace/manifests/ssmp_driver_verification.json`).

## IPL upload

`SPCIPLHost` drives the boot ROM's transfer protocol from the host side of the
ports, following CT's `Audio_Boot` sender (ChronoRET `bankC7.asm`): wait for
`$AA $BB`; send each block's ARAM address in ports 2/3 with token and nonzero
command `$CC` (first) or *last counter + 4, 0 replaced by 1* (later); send each
byte in port 1 with its 8-bit counter in port 0 and wait for the echo; finally
send the entry address with command 0, wait for the echo, and write port 0 = 0.
The host stops **before** the entry instruction executes and only then compares
every uploaded byte with RAM, because the IPL echoes a byte before storing it.
If the CPU leaves `$FFC0...$FFFF` anywhere except the entry it fails at once.
Blocks must not overlap and must lie in `$0200...$FFBF`; total and per-wait
cycle budgets, a stopped CPU and bus faults all fail. A host instance uploads
once. Host writes happen between whole SMP instructions; 65816 timing,
power-on RAM and subcycle port races are not modeled.

No IPL image is bundled. Supply a local 64-byte image:

```sh
macos_studio/.build/debug/chronoforge music driver-check re_workspace/ct_clean.sfc \
  --ipl /path/to/ipl.rom --out driver-check-ipl.json
CHRONOFORGE_IPL_ROM=/path/to/ipl.rom \
  re_workspace/.venv/bin/python macos_studio/tools/verify_ssmp_driver.py --lane ipl
```

With the known image (SHA-256 `c95f88b2…278f`) the six CT payloads, 13,884
bytes, upload with 13,891 acknowledgements in 350,140 SMP clocks (token chain
`$CC $F2 $03 $04 $27 $17`, start token `$17`), match the ROM before `$0200` runs,
and the driver then passes the same checks as the direct load. Upload and
post-entry clocks are reported separately; the first `$0299` entry takes 85,322
post-entry clocks (85,396 when direct-loaded: the timer prescaler phase differs).
One extra check applies: the IPL's start echo stays in CPUIO0 until the driver's
first main-loop pass writes 0. `SPCIPLHostTests` covers the protocol with a
firmware-free receiver model (counter wrap, zero-token correction, stores
committed after their echo, corruption, wrong entry, budgets, stop/fault, input
validation) and runs the real-image lane only when `CHRONOFORGE_IPL_ROM` is set;
without it those tests skip as UNVERIFIED, and a set but invalid path fails.

## Song and sample transfer

`CTSPCTransfer` continues from the booted driver (direct load or IPL upload),
waits for its idle port report, and sends one ROM song the way CT's first song
load after `Audio_Boot` does (`Audio_StartSong`, `Audio_CmdLoadSong` …
`Audio_SendSongData`, `Audio_UploadSample` in ChronoRET `bankC7.asm`). The
original driver receives it (`Spc_CmdSongCheck`, `Spc_StartSong`,
`Spc_XferReceive`/`Spc_XferHeader`, `Spc_XferWords`, `Spc_XferTriples` in
`driver.asm`):

- **Command:** ports 3/2/1 = echo delay, echo word byte 1, song; port 0 = `$10`
  (bit 2 for songs on `Audio_SongBit2List`, empty in US 1.0). After the echo,
  port 1 is the song; bit 7 set means it is already current and nothing follows.
- **Transfers:** a header step carries the ARAM address in ports 2/3 and the
  mode in port 1 (2 = words, 3 = triples) with sequence *(command + 1) & $7F*
  first and `$E0` afterwards; it is accepted when port 1 echoes the mode. Data
  steps follow, the sequence counting mod `$80`. The driver stores nothing below
  `$1E00`.
- **Order:** each listed sample as triples, packed from `$4901` (`$4700` + boot
  block 2); the 64-byte directory at `$1E80`; parameter tables A `$1F40` and B
  `$1FC0` (16 words each); the song at `$2000`, as *length / 3 + 1* triples
  because the sender's BPL loop sends 1–3 bytes past the data; and 36 extra
  bytes at `$F120`.
- **End:** ports 1 and 0 = `$E0`; the driver answers port 1 = 0, starts the song,
  and its main loop then reports port 0 = 0 and the voices in use in port 3.

**Verification point.** Every payload is compared with ARAM at the end
acknowledgement: each mode handler finishes its stores before returning to
`Spc_XferHeader`, the end is echoed only from there, and no song code has run.
They are compared again at the first port report, alongside the driver state
the song start leaves (current/new song, header set and tracks, voice report,
echo delay and buffer from the song's echo word): nine checks in all.

**Step delay.** `Spc_XferTriples` echoes a step after reading port 1 but reads
ports 2/3 later (port 3 is read 14 SMP clocks after the echo). A host that
writes the next step at once replaces those bytes; the tests show it on the
real driver. The host therefore waits 16 SMP clocks after each echo, then
writes every port with port 0 last: a lower bound for CT's fastest loop
(`.extra_loop`, 58 65816 cycles ≈ 16.6 SMP clocks from the echo to its port 3
store). Words steps read both bytes before echoing.

All 83 US songs load and pass. Song `$18` (song data crossing a ROM bank, echo
delay 5 → 6) sends 33,326 bytes in 11,130 steps with 11,145 acknowledgements,
638,040 SMP clocks to the end acknowledgement and 740,649 to the first report.
Over every song the longest load takes 810,539 clocks and the longest single
wait (an echo-delay change before the first report) 293,933; the defaults
allow 4,000,000 in total and 1,000,000 per wait.

```sh
macos_studio/.build/debug/chronoforge music song-load re_workspace/ct_clean.sfc '$18' \
  --out song-load.json                      # add --ipl /path/to/ipl.rom for an IPL boot
re_workspace/.venv/bin/python macos_studio/tools/verify_ssmp_driver.py --lane transfer
```

The song is decimal or `$` hex. The `transfer` lane recomputes every transfer
from the ROM tables in Python, independently of the Swift plan, for four
representative songs (`--all-songs` sweeps all of them), checks CLI refusals,
and compares an IPL boot when `CHRONOFORGE_IPL_ROM` is set. `CTSPCTransferTests`
covers the protocol with a firmware-free receiver model (sequences, late
triples reads, corruption, refusals, budgets, stop/fault, input validation),
transcribes the sender on synthetic tables (bank-crossing copies, the fast
path's in-bank wrap, unused parameter entries), and runs real-ROM and real-IPL
lanes that skip without their local files.

Limits: only the first load after a boot is modeled (every sample slot free,
no `$2F00` block resend, no slot reuse or sound effects); directory entries
past the song's samples are sent as zero, whereas the game sends whatever its
WRAM buffer held; 65816 timing, its timeouts and retries, and subcycle port
races are not modeled. The S-DSP runs during the load; `music render` records
its PCM afterwards.

## S-DSP and PCM rendering

`SDSP` is the sound DSP behind `SSMPBus`: eight voices with BRR decoding and
filter history, 4-tap Gaussian interpolation, pitch and pitch modulation,
ADSR/GAIN envelopes on the hardware rate counter, noise, KON/KOFF/ENDX/FLG,
main and echo volumes, and the echo unit (EDL/ESA buffer in ARAM, EFB, 8-tap
FIR, clamping). It is clocked once per SMP clock and follows the T0-T31 chart
of fullsnes "SNES APU Low Level Timings"; it produces one stereo frame every
32 clocks (32 kHz). The CPU reads the DSP's own ENVX, OUTX and ENDX.

Sources are written documentation, not emulator code: nocash
[fullsnes](https://problemkaputt.de/fullsnes.htm) ("SNES APU DSP BRR Samples",
"BRR Pitch", "ADSR/Gain Envelope", "Volume Registers", "Control Registers",
"Echo Registers", "Low Level Timings") and the SNESdev Wiki (CC0) pages "DSP
envelopes" (counter start, wrap and per-rate offsets) and "S-DSP registers"
(KON polled every second sample). The Gaussian table is fullsnes's 512
entries. `SDSPTests` checks it is non-decreasing with four-tap sums of
`$7FF-$801`, and `tools/compare_libgme.py` finds the same table byte for byte,
interleaved, in the installed libgme binary. Choices fullsnes leaves open are
commented in `SDSP.swift`. Samples are 15-bit after decoding and
interpolation, and the FIR keeps bit 0, with only the echo write masked. A
fresh DSP starts at T2, so the bus's timer ticks land on T1/T17 as the chart
shows.

```sh
macos_studio/.build/debug/chronoforge music render re_workspace/ct_clean.sfc '$18' \
  --seconds 10 --out song.wav --spc start.spc  # add --ipl ipl.rom for an IPL boot
macos_studio/.build/debug/chronoforge music spc-render start.spc --seconds 10 --out replay.wav
```

`render` boots the driver and loads the song as `song-load` does. It refuses
when a load check fails, then records from the driver's first idle port
report. The output is a 32 kHz stereo 16-bit WAV of the DSP's digital output,
before the console's inverting amplifier and analog filter. With `--out`, a
`ct-spc-render/1` JSON report goes to standard output: ROM and IPL hashes,
frames, cycles, PCM SHA-256, peak, the load checks and the limitations.
`--spc` saves the start state. `spc-render` plays any v0.30 snapshot.
`--voices` mixes a subset of voices; muted voices still run. `--counter` and
`--timers-first` choose the restore conventions above. Durations must satisfy
0 < seconds <= 300, rendering has a cycle budget, and errors leave existing
output untouched.

Verification:

- **`SDSPTests`** (ROM-free, values derived by hand from the sources):
  - BRR shifts 0-15, all four filters, 16-bit clipping and 15-bit wrap
  - the Gaussian sum's wrap and saturation
  - the KON delay and poll timing, ADSR attack/decay/sustain, KOFF release
  - ENDX set and clear, end-without-loop muting
  - rate-counter firing for eight rates, and the noise LFSR sequence and period
  - FIR wrap/saturation and tap order, echo feedback `&~1`, output wrap, an echo buffer read/overwrite, FLG mute, snapshot load
- **`SPCRenderTests`**:
  - snapshot export and restore, including the timer convention and `timersBeforeAccess`
  - duration and option refusals, the stereo WAV header, parked-CPU renders
  - a CT render, which skips without the ROM
- **`verify_ssmp_driver.py --lane render`**: the WAV and report agree, rendering is deterministic, the snapshot replays, and CLI refusals hold.
- **`compare_libgme.py`**: renders through the CLI and through libgme 0.6.5 (ctypes, external, never bundled). It accounts for libgme's gain 1.4 (`clamp((s * 358) >> 8)`, filter off), its surround removal and its `$FF` echo-buffer fill at load.

Measured against `/opt/homebrew/lib/libgme.dylib` (sha256 `e4ab17ab…f012`).
Every comparison sits at a constant lag: our frame n-3 is libgme's frame n.

| Comparison | Result |
| --- | --- |
| Exact probe: PMON-source and noise voices, every BRR filter, clamps, shifts 13-15, ADSR, GAIN | Bit-exact from frame 3, except 3 samples where our voice sum saturated before MVOL |
| Exact echo probe: EON, FIR taps 0 and 7, EVOL, EFB 0 | Bit-exact after the first EDL pass |
| Fast-path probe: other volumes, no PMON | 72.6 dB SNR, max \|diff\| 6 |
| Echo feedback probe: EFB, low-pass FIR | 60.8 dB, max 10 |
| Key-on sweep: CPU write at 48 delays | Onsets identical |
| Timer-poll sweep: 72 delays | Identical with libgme conventions; with our defaults one delay differs by 4 frames |
| Songs $04 / $18 / $3F, 6 s, libgme conventions | 52.5 / 50.5 / 51.7 dB, max 7 / 14 / 7 |
| Same songs, our defaults | 20.9 / 32.2 / 33.4 dB, max 4168 / 4143 / 1196 |
| Song $00 | Silent in both |

The residual has three measured causes:

1. **Arithmetic shortcuts.** libgme's default DSP skips per-tap Gaussian rounding and the 15-bit mask for voices that are neither noise nor a PMON source. It also skips the per-voice and per-tap `SAR 6` and the echo `&~1`, and saturates the voice sum only after MVOL, whereas fullsnes saturates after each voice. The exact probes stay on paths where both do the same integer arithmetic. Elsewhere the error stays at 6-14 LSB after gain.
2. **State SPC files do not store.** The rate counter phase: one start (`$7F0`) reproduced libgme's firing for all 31 rates over 12,000 samples, while the SNESdev reset value 0 is our default. The timer prescaler phases are the other part of this state.
3. **One clock-ordering tie.** When the CPU reads T0OUT in the clock its timer ticks, our bus returns the old count and libgme the new one.
   - CT's idle loop polls T0OUT every 25 clocks, so a tie moves the driver's whole tick handler by 25 clocks.
   - In 6 s, songs $04 / $18 / $3F have 49 / 38 / 42 ties among 1,142 ticks.
   - A tie before a KON write can carry the write across a KON poll. In song $04, KON $05 lands at clock 263,826 in ours, 20 clocks after a poll, and libgme keys on one poll (2 samples) earlier.
   - With `--timers-first` and `--counter 0x7F0`, songs fall to the rounding level above.

Song PCM is therefore not bit-exact with libgme, and neither model is shown to
be the hardware's.

Limits:

- The live render is the zero-state boot model: counter 0, access before clock, no host commands after the load (no sound effects, fades or song changes).
- Only the digital output is rendered.
- A debug build renders about 0.7x real time (10 s of song in 14.6 s). Release speed is unmeasured.

## Remaining playback work

1. Extend the normal-speed bus beyond its documented limits only with reference
   evidence: physical edge timing (including the access/timer order within a
   clock, above), TEST modes and hardware reset/restore.
2. CT host: the IPL boot, driver initialization and the first song load (song
   and samples through the driver's transfer commands) execute and verify.
   Later loads (slot reuse, the `$2F00` block resend, sound effects) and the
   65816 sender's own timing remain.
3. Studio playback through AVFoundation (real-time S-DSP, a Play control).
   `music render` writes WAV files; Studio has no Play control yet.
4. `BRR.decode` (the asset pipeline, kept in parity with `ct_audio.py`) treats
   shifts 13-15 differently from the S-DSP rule above (nibble `SAR 3`, then
   `SHL 11`), which libgme confirms; reconcile it separately.
